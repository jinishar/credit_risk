# AI-Powered Credit Risk Intelligence Platform

A lightweight, end-to-end AI platform on the Kaggle **Home Credit Default Risk**
dataset: EDA → an imbalance-aware ML default-risk model → SHAP explainability
→ business rule derivation → a Gemini-powered talk-to-data chatbot → one
multi-tab Streamlit UI → Docker Compose deployment.

> **Important — synthetic data notice.** No real `application_train.csv` was
> available while building this (only Kaggle's 220-row column *dictionary*
> was provided, not applicant records). The platform therefore generates a
> **schema-accurate synthetic dataset** on first run — same 122 columns, same
> ~13% class imbalance, same known data-quality quirks (e.g. the
> `DAYS_EMPLOYED == 365243` anomaly), with deliberate correlations so the
> model/SHAP/EDA have genuine signal to find. **Drop the real
> `application_train.csv` (and `application_test.csv`) from
> [the Kaggle competition](https://www.kaggle.com/competitions/home-credit-default-risk/data)
> into `data/` and everything below works unchanged — zero code edits
> required.** See [Known Limitations](#known-limitations--improvements).

```
      (LogReg baseline + LightGBM,            nl_to_sql.py         (Gemini + validator)

               │

         Docker Compose (single `app` service, DuckDB + volumes for data/models)
```

**Why these choices:**
- **DuckDB, not Postgres** — the chatbot needs SQL, but there's no reason to run
  a second container for it; DuckDB is embedded, fast for analytical
  queries, and reads the same CSV the ML pipeline uses, so both layers stay
  perfectly in sync with zero duplication.
- **LightGBM + Logistic Regression baseline, not deep learning** — the data
  is small/medium tabular with heavy missingness and mixed types; LightGBM
  handles both natively, trains in seconds (fits "lightweight platform"),
  and is exactly explainable via SHAP's fast `TreeExplainer`. Logistic
  Regression is trained alongside as an interpretable sanity-check baseline;
  the model with the higher validation ROC-AUC is promoted automatically.
- **`src/ml/explain.py`, `src/rules/`, `app/`** — the assignment's own
  published folder tree (in `Docs/NeoStats_AI_Use_Case.pdf`) has no slot for
  SHAP explainability, the rule-derivation module, or the UI code, even
  though all three are separately required deliverables in that same
  document. These three additions are the only deviations from the
  published tree; everything else (`data/`, `notebooks/`, `src/data`,
  `src/ml`, `src/talk_to_data`, `src/utils`, `sql/`, `models/`, `Dockerfile`,
  `docker-compose.yml`, `requirements.txt`, `.gitignore`, `README.md`)
  matches it exactly.

## Setup & Run

### Option A — Docker (recommended, one command)

```bash
cp .env.example .env        # optionally add GEMINI_API_KEY for the chatbot
docker-compose up
```

Open **http://localhost:8501**. On first start the container automatically
generates the dataset (synthetic, or real if you've dropped CSVs into
`data/`), trains the model, and derives business rules (~60-90s); subsequent
restarts reuse the artifacts already in the mounted `models/` volume and
start instantly.

### Option B — Local Python

```bash
python -m venv .venv && source .venv/bin/activate   # or .venv\Scripts\activate on Windows
pip install -r requirements.txt
cp .env.example .env        # optionally add GEMINI_API_KEY
python -m src.ml.train
python -m src.rules.rule_engine
streamlit run app/streamlit_app.py
```

### Using the real dataset instead of synthetic data

Download `application_train.csv` (and optionally `application_test.csv`)
from the [Kaggle competition](https://www.kaggle.com/competitions/home-credit-default-risk/data)
and place them in `data/`. `src/data/loader.py` uses real files if present
and only falls back to `src/data/synthetic.py` when they're missing — no
other code changes needed. Delete `models/*` and `data/credit_risk.duckdb`
first so the pipeline retrains on the new data.

## Model Selection & Class Imbalance Strategy

Two models are trained and compared on a stratified 80/20 split:

| Model | ROC-AUC | PR-AUC |
|---|---|---|
| Logistic Regression (`class_weight='balanced'`) — baseline | 0.725 | 0.307 |
| **LightGBM (`scale_pos_weight`) — champion** | **0.859** | **0.438** |

LightGBM is promoted automatically (higher ROC-AUC). Chosen over a deep
model because the data is tabular with heavy missingness and mixed
numeric/categorical types — LightGBM handles both natively, trains in
seconds on this dataset size, and pairs with a fast, exact SHAP
`TreeExplainer`.

**Imbalance handling** (~13% positive class in the generated data, ~6.7:1
ratio): `class_weight='balanced'` for Logistic Regression, `scale_pos_weight`
(negative/positive ratio ≈ 6.7) for LightGBM. No SMOTE/oversampling was used,
to avoid compounding synthetic correlations on top of already-synthetic
data — see [Known Limitations](#known-limitations--improvements) for the
real-data recommendation.

**Probability calibration (a bug caught during testing):** `scale_pos_weight`
fixes *ranking* quality (ROC-AUC/PR-AUC are unaffected) but distorts raw
probabilities — the uncalibrated champion's predicted probabilities topped
out at **0.41**, meaning the "High" risk band (>0.5) could never fire. Fixed
with `CalibratedClassifierCV(method="isotonic", cv="prefit")` on the
held-out validation fold, remapping scores to the applicants' true empirical
default rates. After calibration, probabilities span the full 0-1 range and
all three bands are reachable (on the validation set: ~78% Low, ~21%
Medium, ~2% High).

**Risk bands** (`src/utils/helpers.py::risk_band`, thresholds in `.env`):
Low `< 0.2`, Medium `0.2 – 0.5`, High `> 0.5`.

## Evaluation Metrics & Results

From `models/metrics.json` (regenerate with `python -m src.ml.train`):

```
Champion: LightGBM + isotonic calibration
  ROC-AUC:    0.862
  PR-AUC:     0.436
  F1 @ 0.5:   0.170   (precision 0.668, recall 0.098)
  Confusion matrix @ 0.5: TN=8637  FP=63  FN=1173  TP=127
```

ROC-AUC/PR-AUC are the headline metrics rather than accuracy or a fixed-0.5
F1: with ~87/13 class split, a model that always predicts "no default"
scores ~87% accuracy while being useless, and the *actual* decision
threshold a bank uses should be set from business risk appetite (a
precision/recall trade-off), not hard-coded at 0.5 — which is exactly why
the risk bands operate on the raw calibrated probability instead of a single
classification cutoff.

## Explainable AI

SHAP `TreeExplainer` (`src/ml/explain.py`) on the underlying LightGBM
booster (unwrapped from the calibration wrapper for exact tree attributions).
Chosen over LIME because it's exact (no local sampling) and fast enough for
interactive per-applicant explanations, and gives both a global
feature-importance view and a signed, additive per-prediction breakdown from
the same explainer.

Top global drivers found: `CREDIT_INCOME_RATIO`, `EXT_SOURCE_MEAN`, housing
type, education level, individual `EXT_SOURCE_1/2/3` scores — all
business-sensible. The Explainability tab shows the top contributing
features for whichever applicant was just scored, each labeled "increases
risk" / "decreases risk" rather than exposing raw SHAP log-odds numbers,
which would be meaningless to a non-technical user.

## Business Rule Derivation

`src/rules/rule_engine.py` produces two complementary, audit-friendly rule
types (spec's "bridge ML insights and credit policy with rules"):

1. **Surrogate decision tree** (depth ≤3) trained to mimic the champion
   model's predictions — every root-to-leaf path is a readable IF/THEN rule
   a credit analyst can review, e.g.:
   ```
   IF CREDIT_INCOME_RATIO <= 8.04 AND EXT_SOURCE_MEAN <= 0.299
      AND NOT NAME_HOUSING_TYPE = House/apartment
   → predicted default rate 54.1% (310 applicants)
   ```
   ```
   IF CREDIT_INCOME_RATIO <= 8.04 AND EXT_SOURCE_MEAN > 0.299
      AND NAME_HOUSING_TYPE = House/apartment
   → predicted default rate 4.2% (13,527 applicants)
   ```
2. **Threshold bins** on the top SHAP feature (`CREDIT_INCOME_RATIO`),
   reporting the *observed* (not model-predicted) default rate per quantile —
   grounded directly in data:
   ```
   CREDIT_INCOME_RATIO in (6.9, 58.4]  → observed default rate 33.5%
   CREDIT_INCOME_RATIO in (1.8, 2.89]  → observed default rate  8.0%
   ```

Both rule sets are shown in the UI's Business Rules tab, alongside which
rules the currently-scored applicant triggers.

## Talk-to-Data: Prompt Engineering & Token Optimization

`src/talk_to_data/` (Gemini via `google-genai`):

- **Two-tier answering** (`nl_to_sql.py`): the 5 required guaranteed query
  patterns are matched by keyword *before* ever calling the LLM, so they're
  100% reliable and hallucination-free. Everything else falls through to
  Gemini. This is the main hallucination-control mechanism — deterministic
  answers where correctness matters most, LLM only for genuine long-tail
  questions.
- **SQL validation** (`nl_to_sql.py::validate_sql`): every LLM-generated
  query is parsed with `sqlparse` and rejected unless it is a single
  `SELECT` statement referencing only the whitelisted `applications` table,
  with no DDL/DML/administrative keywords. Tested against
  `DROP TABLE applications`, stacked `SELECT ...; DELETE ...`, and
  cross-table access — all correctly rejected (see `nl_to_sql.py`'s
  `__main__` block). `query_runner.py` also caps result size, appending
  `LIMIT 200` if the query didn't already include one.
- **Token optimization**: the system prompt sends a curated ~25-column
  schema summary (`prompt_templates.SCHEMA_CONTEXT`), not the full
  121-column dictionary; conversation memory sent on follow-ups is a list of
  prior `(question, sql)` pairs capped at the last 4 turns, never raw result
  tables; and result narration is built from a truncated preview (≤15 rows)
  rather than the full result set.
- **Conversation memory**: `ChatSession.history` (in `query_runner.py`)
  lets follow-ups like "and for women only?" resolve against the previous
  question's SQL.
- **Graceful degradation without a key**: with no `GEMINI_API_KEY` set, the
  5 canonical questions still run end-to-end (SQL executes, and narration
  falls back to a plain templated summary of the result); only genuinely
  free-form questions require the key.

### Sample chatbot output (captured, no Gemini key needed for these)

| Question | SQL generated | Result |
|---|---|---|
| What is the overall default rate? | `SELECT AVG(TARGET)*100 AS default_rate_pct, COUNT(*) AS n_applicants FROM applications` | 13.0%, 50,000 applicants |
| How many applicants own both a car and a house? | `SELECT COUNT(*) FROM applications WHERE FLAG_OWN_CAR='Y' AND FLAG_OWN_REALTY='Y'` | 12,601 |
| Show default rate by education level | `SELECT NAME_EDUCATION_TYPE, AVG(TARGET)*100 ... GROUP BY ...` | Lower secondary 27.1% → Academic degree 7.5% |

With a real `GEMINI_API_KEY`, free-form questions (e.g. "what's the median
annuity for revolving loans in the trade sector?") are additionally
supported through the validated Gemini path.

## EDA — Key Findings

Full analysis in `notebooks/eda.py` / `notebooks/eda.ipynb`, figures in
`notebooks/figures/`. Headline findings on the generated dataset (50,000
rows, 122 columns, ~13% default rate, 6.7:1 imbalance):

1. **Default rate by education**: 7.5% (Academic degree) → 27.1% (Lower
   secondary).
2. **Default rate by credit-to-income ratio quintile**: 8% for the bottom 4
   quintiles, jumping to 32% for the top quintile (ratio > ~6.9) — the
   single strongest lever found.
3. **External credit scores** (`EXT_SOURCE_1/2/3`) are the strongest
   continuous predictors, each correlating ≈ -0.15 with `TARGET`.
4. **Family status**: Married/Widowed applicants default less (11-12%) than
   Single/Civil-marriage applicants (17-18%).
5. **Data quality**: 47 of 122 columns have >50% missing values, dominated
   by the building/apartment-info block (`*_AVG/_MODE/_MEDI`, ~55% missing
   each). `DAYS_EMPLOYED` contains the well-known `365243` placeholder
   ("not currently employed") in ~18% of rows — handled explicitly in
   `preprocessor.py` as a separate anomaly flag rather than treated as a
   real day count.
6. *(bonus)* Age: the 65+ bracket defaults noticeably less (7.6%) than
   working-age brackets (~13%).

## Known Limitations & Improvements

- **Synthetic data.** The single biggest limitation — see the notice at the
  top. Real-world feature interactions, fraud patterns, and the exact
  8.07% base rate will differ from what's modeled here. Swap in the real
  Kaggle CSV to get a production-representative model (loader requires zero
  code changes).
- **Calibration fit on the same fold it's evaluated on** is mildly
  optimistic (`CalibratedClassifierCV(cv="prefit")` on `X_val`/`y_val`, then
  evaluated on that same fold). With more data, calibrate on a third
  held-out split distinct from both training and evaluation.
- **No bureau/previous-application tables.** Only `application_train/test`
  is used (a deliberate scope decision for a "lightweight platform" — see
  the assignment conversation). Joining `bureau.csv`,
  `previous_application.csv`, `installments_payments.csv` etc. would add
  meaningful predictive signal (repayment history) at the cost of
  significantly more ETL complexity.
- **No SMOTE/oversampling.** `scale_pos_weight`/`class_weight='balanced'`
  were used instead, to avoid compounding synthetic correlations on top of
  synthetic data. With real data, SMOTE or borderline-SMOTE on the training
  fold only (never on validation/test) is worth A/B-testing against the
  current approach.
- **Chatbot free-form questions require a Gemini key.** The 5 canonical
  patterns work without one; add `GEMINI_API_KEY` to `.env` to unlock
  open-ended questions.
- **Presentation PDF not included** — see `documents/PRESENTATION_TODO.md`;
  it requires screenshots of the actually-running app, which must be
  captured by whoever runs it.
- **Surrogate-tree rules approximate, not exactly reproduce, the LightGBM
  model.** They're intentionally shallow (depth ≤3) for human readability;
  treat them as policy guidance, not a drop-in replacement for the model's
  own score.
